# v1.2 specification

**Theme:** encrypted transport.

Since v1.0 the token keeps strangers out, and since v1.1 it also unlocks
controls in the browser. But the token, every command and every device state
cross the network in plain text, over plain TCP and plain HTTP. Anyone who can
watch the Wi-Fi traffic can read the token and then switch every device in the
house. v1.2 encrypts both connections with TLS, using certificates the project
makes for itself.

Written as an implementation brief, the same way as
[v1.1-spec.md](v1.1-spec.md): every decision below is already made, so the work
is to build it, not to redesign it. Where something was deliberately left out,
it says so and why.

## Scope

**In**

1. A certificate tool: a private certificate authority for this house and a
   server certificate signed by it
2. TLS on the client connection
3. HTTPS for the dashboard

**Out, and why**

| Not doing | Reason |
| --- | --- |
| Public certificates (Let's Encrypt) | They need a public domain name and a server reachable from the internet. A home LAN has neither. |
| Client certificates (mutual TLS) | The token already says who may connect. A certificate per device is more to make, copy and renew for no gain at this size. |
| Plain HTTP redirecting to HTTPS | A second listener on another port for one redirect. The address printed at startup is already `https://`. |
| Automatic renewal | The server certificate is valid for 825 days. Renewing is one command that keeps the authority, so nothing needs reinstalling. |
| Refusing to start without TLS | Upgrading must not lock anyone out. Without certificates everything works as in 1.1, with a warning, the same way a missing `TOKEN` is handled. |
| Encrypting the config files | The token on disk is protected by the computer's own account. That is a different problem. |

## Why a private authority, and not one self-signed certificate

A self-signed server certificate would be one file. But a phone that trusts it
has to trust it again every time it is made anew, and it must be made anew
whenever the server's address changes. With a private authority:

- the phone and every client trust **one** file, `ca.crt`, once
- the server certificate can be remade any time (new IP address, expiry)
  without touching a single phone or client
- the authority's key `ca.key` signs nothing else, so trusting it trusts only
  this house's server

## Part 1: Certificates

### Problem

TLS needs a certificate and a key on the server and something the clients and
the browser trust. Windows has no `openssl` command by default, so the project
makes its own.

### Design

**A tool, `server/make_certs.py`.** It uses the `cryptography` package, which
joins `fastapi` and `uvicorn` in `requirements.txt`. The client still needs
nothing beyond the standard library: it only reads `ca.crt`, which Python's
`ssl` module does on its own.

```
py server/make_certs.py
```

writes into `server/data/certs/`:

| File | What it is | Secret | Goes to |
| --- | --- | --- | --- |
| `ca.key` | the authority's private key | **yes** | stays on the server computer, nowhere else |
| `ca.crt` | the authority's certificate | no | every client and every phone |
| `server.key` | the server's private key | **yes** | stays with the server |
| `server.crt` | the server's certificate, signed by `ca.key` | no | stays with the server |

**What gets made.**

| | Authority | Server certificate |
| --- | --- | --- |
| Key | EC P-256 | EC P-256 |
| Valid | 10 years | 825 days, the longest Apple devices accept |
| Name | `pyhome CA <hostname>` | `pyhome server` |
| Extensions | `BasicConstraints(ca=True, path_length=0)`, `KeyUsage(cert_sign, crl_sign)` | `BasicConstraints(ca=False)`, `ExtendedKeyUsage(server_auth)` |
| Subject alternative names | none | `localhost`, `127.0.0.1`, the computer's host name, `<hostname>.local`, the LAN address from `shared.network.get_local_ip()`, plus any `--host` given |

The names matter for the browser: it refuses a certificate whose names do not
include the address in the address bar. `--host 192.168.1.50 --host dom.lan`
adds more.

**Running it again keeps the authority.** If `ca.key` and `ca.crt` exist, only
`server.key` and `server.crt` are made anew. That is the renewal and the fix
for a changed address, and no phone or client needs anything new. `--new-ca`
starts over and says loudly that every client and phone must get the new
`ca.crt`.

**It prints the next steps**, with the real paths:

```
Certificates written to server/data/certs
  server.crt valid until 2029-01-24 for localhost, 127.0.0.1, DOM-PC, DOM-PC.local, 192.168.1.20

Next:
  1. server/data/config.json:  "TLS_CERT": "certs/server.crt", "TLS_KEY": "certs/server.key"
  2. copy certs/ca.crt to every client's data/certs/ folder
     and set "TLS_CA": "certs/ca.crt" in its config
  3. install ca.crt on phones that open the dashboard, see README
Keep ca.key and server.key private.
```

**Config keys.** Paths are relative to the folder of the config file in use,
so `--config` instances work the same way `clients.json` does.

| Key | Side | Meaning |
| --- | --- | --- |
| `TLS_CERT` | server | the server certificate. Empty: no TLS |
| `TLS_KEY` | server | its private key |
| `TLS_CA` | client | the authority's certificate to trust. Empty: plain TCP |

Both default configs get the keys, empty.

**Git.** `.gitignore` gains `**/certs/`. Keys must never be committed, and
`ca.crt` belongs to one house, not to the project.

### Done when

`py server/make_certs.py` on a fresh checkout writes the four files and prints
the steps; running it again leaves `ca.crt` byte for byte the same and makes a
new `server.crt` that `ca.crt` still verifies; `git status` shows none of them.

## Part 2: TLS on the client connection

### Design

**Server.** When `TLS_CERT` is set, `start_server_async` builds an
`ssl.SSLContext` with `ssl.create_default_context(ssl.Purpose.CLIENT_AUTH)` and
`load_cert_chain(cert, key)`, and passes it to `asyncio.start_server(ssl=...)`.
The rest of the server does not change: `reader` and `writer` hide TLS
completely, framing and messages are the same.

A cert or key that cannot be loaded (missing file, broken file, a key that
does not match the certificate) stops the server at startup with the reason. Running without
encryption because of a typo would be the worst outcome, it would look like it
works.

**Client.** When `TLS_CA` is set, `handshake()` builds
`ssl.create_default_context(cafile=<TLS_CA>)` with `check_hostname = False`
and passes it to `asyncio.open_connection(ssl=..., ssl_handshake_timeout=10)`.

**Why `check_hostname` is off.** The chain is still fully verified: only a
certificate signed by this house's `ca.key` is accepted. Host name checking
would add a second rule, that the certificate names the exact `HOST` the
client dials. That rule protects against a certificate from a public authority
issued for someone else, which cannot happen here, because `ca.key` signs only
this server. Leaving it on would break every client the day the server gets a
new IP address, until the certificate is remade. The browser keeps its own
check on, it has no choice, see Part 3.

**Startup lines.** The server prints `TLS on, certificate valid until
<date>`, or a warning when it has none:

```
! No TLS_CERT set, the token and every message cross the network in plain text
```

The client prints `TLS on, trusting <ca.crt path>` or the same kind of
warning. A certificate that expires within 30 days adds a warning at server
startup with the command that renews it.

**When the two sides disagree.** Each case must end in a readable line on the
client, never a silent retry loop:

| Server | Client | What happens | Client prints | Retries |
| --- | --- | --- | --- | --- |
| TLS | TLS, trusts the CA | connects | `Connected to ... (TLS)` | |
| TLS | TLS, other CA or none | certificate rejected | `Server certificate not trusted by TLS_CA: <reason>. Fix TLS_CA in <config>, then type 'reconnect'.` | **no**, like a refused token |
| TLS | plain | server closes during the handshake | `Server closed the connection during the handshake. If it uses TLS, set TLS_CA in <config>.` | yes |
| plain | TLS | handshake fails | `TLS handshake failed: <reason>. If the server does not use TLS, empty TLS_CA in <config>.` | yes |
| TLS | TLS, `TLS_CA` file missing | context cannot be built | `TLS_CA file not found: <path>` | **no** |

A rejected certificate or a missing `TLS_CA` file will not fix itself, so the
client stops retrying, exactly as it does for a refused token, and `reconnect`
re-reads the config. The two mismatch rows keep retrying: the server may be
mid restart with its new config.

`ssl.SSLCertVerificationError` is a subclass of `OSError`, so it has to be
caught before the existing `except OSError` in `connect_to_server_async`, the
same trap as `TimeoutError` in v1.1.

### Done when

With certificates made and both configs set, a client connects and `about` on
both sides says TLS is on; the same token that 1.1 sent in plain text no longer
appears in a capture of the traffic (the end to end test checks this by
listening on a proxy socket between client and server); a client trusting
another authority is refused and stops retrying; and a client and server
without any TLS settings work exactly as in 1.1, with a warning each.

## Part 3: HTTPS for the dashboard

### Design

**Server.** With `TLS_CERT` set, `start_web` passes `ssl_certfile` and
`ssl_keyfile` to `uvicorn.Config`. The same port, `WEB_PORT`, now speaks HTTPS
only. The addresses printed at startup become `https://`.

**The browser checks names.** Unlike the client, the browser insists that the
certificate names the address in the address bar. That is why Part 1 puts the
host name, `.local` name and LAN address in the certificate, and why a changed
address means running `make_certs.py` again (a few seconds, phones keep their
trust).

**Phones and computers trust `ca.crt` once.** Without that, the browser shows
a full page warning on every visit. The README gets a short guide:

- **Android** (menu names vary by maker): Settings → Security → Encryption & credentials → Install a
  certificate → CA certificate, pick `ca.crt`
- **iPhone:** send `ca.crt` to the phone (AirDrop, mail), install the profile
  in Settings, then turn it on in Settings → General → About → Certificate
  Trust Settings
- **Windows:** double click `ca.crt` → Install Certificate → Local Machine →
  Trusted Root Certification Authorities

**`/ca.crt` on the dashboard.** The page serves the authority certificate at
`GET /ca.crt` without a token, so a phone can download it from the server it
is about to trust. It is public by nature, the key stays behind. The login
card gets one line: "Prvé pripojenie z tohto zariadenia? Stiahni ca.crt".

There is a chicken and egg here: the first download is over HTTPS the phone
does not trust yet, so the browser warns once. Accepting that once to fetch
the file is fine, and the README says to compare the fingerprint the server
prints at startup with the one the phone shows, which is what makes it safe.

**The stored token.** `localStorage` belongs to an origin, and
`http://dom:50001` and `https://dom:50001` are different origins. After the
switch the page asks for the token once more. The README says so.

### Done when

With certificates made, the dashboard answers on `https://` and not on
`http://`; a Python client trusting `ca.crt` reads `/api/status` with full
verification, host name included, at `https://localhost:<port>`;
`/ca.crt` returns the authority certificate without a token; and a server
without TLS serves plain HTTP as in 1.1.

## Protocol

**No change.** TLS wraps the same newline framed JSON. A 1.1 client works with
a 1.2 server as long as neither side has TLS set.

## Order of work

1. **Certificates** first. Nothing else can be tested without them.
2. **TLS on the client connection** second: it carries the token from every
   device.
3. **HTTPS** last. It reuses Part 1's files and adds only the browser side.

Each part gets its own implementation plan in `docs/superpowers/plans/`, is
built and verified in a scratch checkout first, and is finished, tested and
committed before the next one starts.

## Tests

Plain scripts with asserts, as in `tests/`, run by `py tests/run_all.py`.
`cryptography` is needed for the tests that make certificates, like `fastapi`
already is for the server tests.

- **Part 1:** the four files exist with the right extensions, names and
  validity; the server certificate verifies against `ca.crt`; a second run
  keeps the authority and makes a new server certificate; `--new-ca` makes a
  new authority; `--host` adds names; the printed steps name the real paths;
  paths in config resolve against the config's folder
- **Part 2:** a TLS server and client in one process (as `test_client_connection.py`
  does with plain sockets); every row of the mismatch table; the token does not
  appear in the bytes on the wire; startup warnings with and without TLS
- **Part 3:** HTTPS with full verification against `ca.crt`; plain HTTP to the
  HTTPS port fails; `/ca.crt` without a token; an end to end run of 1.1's
  dashboard tests over HTTPS

The phone install is checked by hand and written down in Part 3's plan.

## Honest limits

- **The first trust is on you.** Installing `ca.crt` on a phone is what makes
  HTTPS mean anything. Compare the fingerprint, or copy the file over a cable.
- **`ca.key` is the key to the house.** Anyone who has it can make a server
  certificate every client and phone will trust. It stays on the server
  computer, out of git, out of backups that leave the house.
- **Encryption is not authorization.** TLS hides the token, it does not change
  who may use it. One token still opens everything, as in 1.1.
- **The server computer itself is trusted.** Configs and keys lie on its disk
  unencrypted.

## Version

`VERSION` in both default configs becomes `1.2`. `docs/versions/v1.2.md` is
written when the version is finished, and its row in the README roadmap is
struck.
