# v1.0 specification

**Theme:** several devices at once, safely.

v0.9 gave the project a shared package and a framed protocol, but it can still
only run one client per checkout, that client cannot do anything except print
text, and anyone who can reach the port is let in. v1.0 closes all three.

Written as an implementation brief: every decision below is already made, so the
work is to build it, not to redesign it. Where something was deliberately left
out, it says so and why.

## Scope

**In**

1. Per instance configuration, so one checkout runs several clients
2. Device modules, so a client declares what it is and what it can do
3. A shared token checked during the handshake

**Out, and why**

| Not doing | Reason |
| --- | --- |
| TLS | The token stops casual access on a home LAN. Real transport security is a separate piece of work and needs certificates. |
| Dashboard controls | The dashboard stays read only. Sending commands from the browser needs the web handler to reach into the client registry, which is worth its own version. |
| `clients.json` as a dict keyed by id | The list works fine at this size and changing it means migrating existing files for no gain yet. |
| Persisting device state | The server keeps the last known state in memory only. Losing it on restart is acceptable, the client can be asked again. |
| Pairing or discovery UI | Configuration files are enough while the devices are set up by hand. |

## Part 1: Per instance configuration

### Problem

`ID` is fixed in `data/config.json`. Two clients started from the same folder
report the same id, so they overwrite each other in `clients.json` and the
`list` command and the dashboard collapse them into one row.

### Design

The config file becomes a command line argument:

```
py app.py                                 uses data/config.json
py app.py --config data/kitchen.json      uses that file
```

`shared/config.py` already funnels everything through `init()`, so this is a
small change:

```python
def init(app_dir, config_file=None):
    """config_file overrides the default <app_dir>/data/config.json."""
```

`app.py` parses the argument before calling `init()`. One optional argument does
not justify `argparse`, reading `sys.argv` is enough, but either is fine.

### Identity

If `ID` is missing or empty when the config loads, generate one and write it
back:

```python
ID = uuid4().hex[:8]
```

Eight hex characters stay readable in the console while being unique in
practice. This means a new config file only needs `NAME`, `DEVICE` and the
network settings (`HOST`, `PORT`), and the first run stamps its own identity.
Existing configs keep the ids they have.

### Launcher

A small GUI replaces `start_all.bat`, which is deleted. Starting several clients
by hand means one console and one command per config, and a batch file that
takes config names is no easier to use than that.

`launcher.pyw` in the repo root, `tkinter` and `subprocess` only, so it needs
nothing installed and double clicking it opens no empty console of its own.

```
┌ Smart home launcher ───────────────────────┐
│ Server                                     │
│  [x] server/data/config.json      ● running│
│ Clients                                    │
│  [x] config.json    (no device)   ○ stopped│
│  [x] kitchen.json   light         ● running│
│  [ ] bedroom.json   thermostat    ○ stopped│
│                                            │
│  [Run]   [Stop all]   [Refresh]            │
└────────────────────────────────────────────┘
```

- **What it lists.** Clients are every `client/data/*.json`, shown with `NAME`
  and `DEVICE`. A config file is an instance, the thing you tick, which keeps
  each device's id stable between runs. The server is only
  `server/data/config.json` for now. `server/data` is not scanned because
  `clients.json` lives there too. Choosing between several servers comes later.
- **Run** starts the server first if it is ticked, then every ticked client
  that is not already running:
  `Popen([python_executable(), "app.py", "--config", path], cwd=app_dir, creationflags=CREATE_NEW_CONSOLE)`.
  `python_executable()` swaps a `pythonw.exe` interpreter for `python.exe`, so
  double clicking the `.pyw` launcher still opens a console for each app.
  Python is started directly rather than through `cmd`, so the launcher holds
  the real process and can tell whether it is alive and stop it. Starting the
  server does not wait for it to actually be listening, so Run gives it a 2 s
  head start before starting any ticked client. Configs whose `ID` collides
  with another are refused: their row is disabled and shows the clash.
- **Status** comes from `poll()` about once a second: running, stopped, or
  exited with code N.
- **Stop** on each row and **Stop all** use `terminate()`. The server sees this
  as an ordinary dropped connection. A clean `shutdown` would need the launcher
  to type into the app's console, which a separate console does not allow.
- **Closing the launcher** while apps run asks whether to stop them: yes, no
  (leave them running) or cancel.
- `client/start.bat` and `server/start.bat` stay, for starting one app by hand.

Because the app is no longer started through a batch file ending in `pause`,
its window would close the moment it crashes. The `Fatal error` branch in both
`app.py` files waits for Enter so the error can be read.

Not in the launcher, each can come later: creating or editing configs,
remembering the last selection, showing app output inside the launcher.

### Also

- The window title already uses `NAME#ID`, so several clients are
  distinguishable on the taskbar once their ids differ.
- The README drops `start_all.bat` for the launcher.

### Done when

Three clients started from the launcher with three config files appear as
three separate rows in `list` and on the dashboard, each with its own address,
and Stop all ends every one of them.

## Part 2: Device modules

This is the heart of v1.0. A client stops being a chat program and becomes a
thing that can be told to do something.

### Structure

```
client/
├── devices/
│   ├── __init__.py
│   ├── light/
│   │   └── __init__.py   the contract below
│   └── thermostat/
│       └── __init__.py
└── data/config.json      gains "DEVICE": "light"
```

Each device is a package rather than a single file, so it has room for files
of its own next to the contract, a hardware driver for example. `DEVICE` names
the folder.

### The contract

A device package declares itself in its `__init__.py` the same way a command
module does, by module level names rather than classes or decorators, so the
two feel alike:

```python
device = "light"
description = "Dimmable light"

async def turn_on(**params):
    ...

async def turn_off(**params):
    ...

async def set_brightness(level=100, **params):
    ...

async def get_state():
    return {"on": True, "brightness": 80}

# what this device accepts, get_state is implied and always available
actions = [turn_on, turn_off, set_brightness]
```

Capabilities are derived as `[f.__name__ for f in actions]`, so the list is
declared once and cannot drift from the functions.

### Loading

A new `client/handlers/device_handler.py`, modelled on `shared/command_handler.py`:

```python
load_device(devices_dir, package, name)   # imports the package named by DEVICE
get_device()                              # the loaded module, or None
get_capabilities()                        # list of action names
async run_action(name, params)            # dispatch, raises on unknown action
```

A client with no `DEVICE` set loads nothing and reports an empty capability
list. That keeps a plain message only client working exactly as it does now.

Devices load from `client/devices/` only. Loading them from several folders the
way commands do is possible later, but nothing needs it yet.

### Protocol additions

`hello` gains two fields:

| Field | Meaning |
| --- | --- |
| `device` | the value of `DEVICE`, or `null` |
| `capabilities` | list of action names, empty when there is no device |

The existing `device_type` field in `hello` (and in the server's `welcome`) is
renamed to `role`. It carries the config's `TYPE`, which is `"client"` or
`"server"`, the role of the app. Next to the new `device` field the old name
would read as the kind of device, which is what `device` now means. The config
key `TYPE` itself stays as it is. The README protocol table follows the
rename.

Three new message types:

| Type | Direction | Fields |
| --- | --- | --- |
| `cmd` | server to client | `action`, `params` (object), `request_id` |
| `result` | client to server | `request_id`, `ok` (bool), `state` or `error` |
| `state` | client to server | `state` (object), sent unprompted |

`request_id` is a short uuid the server generates. It exists so a reply can be
matched to its request once more than one command is in flight. Without it the
server can only guess which answer belongs to which question.

A client that receives `cmd` for an action it does not have replies with
`ok: false` and an `error`, rather than closing the connection. Unknown message
types keep being ignored, as v0.9 already does.

### Server side

`connected_clients` gains `device`, `capabilities` and `last_state` per client.

A new command:

```
do <id> <action> [key=value ...]
```

for example `do a3f1b2c4 set_brightness level=40`. Values parse as int, float,
`true`/`false`, otherwise string. The command waits for the matching `result`
with a timeout of a few seconds and prints what came back.

`list` shows the device type next to each online client. `state <id>` is
shorthand for `do <id> get_state`.

The dashboard gains device and capabilities columns, and shows the last known
state. Still read only.

### Done when

A light client and a thermostat client are connected at once, `list` shows what
each one is, `do <id> set_brightness level=40` prints a successful result from
the right client, and asking a thermostat to set brightness fails cleanly
without dropping the connection.

## Part 3: Token during the handshake

### Design

Both configs gain a `TOKEN` field. The client sends it in `hello`, the server
compares it with its own and answers `denied` before closing if it does not
match:

| Type | Direction | Fields |
| --- | --- | --- |
| `denied` | server to client | `reason` |

The client prints the reason and does not retry with the same token, since
retrying cannot start working on its own.

### Compatibility

If the server's `TOKEN` is empty or missing, every client is accepted and the
server prints a warning at startup. Upgrading does not lock anyone out, and the
warning makes the open door visible rather than silent.

### Honest limits

The token travels in plain text over a plain socket. It stops a neighbour or a
stray device on the same network, it does not stop anyone who can watch the
traffic. Say so in the README rather than implying the system is secure.

### Done when

A client with the wrong token is refused with a readable reason, a client with
the right one connects, and a server with no token set still accepts everyone
while saying so at startup.

## Order of work

1. **Per instance configuration** first, launcher included. Until several
   clients can run at once, device modules cannot really be tested.
2. **Device modules** second, the largest piece.
3. **Token** last. It touches only the handshake and is easy to add once the
   handshake carries device information anyway.

## Tests

v0.9 was verified with throwaway scripts that no longer exist. v1.0 adds enough
protocol surface that this should not be repeated. Add a `tests/` folder holding
what those scripts did:

- start the real server, connect real clients over a socket, assert on the
  handshake and the dashboard API
- several messages in one write, a message split across two writes, and a
  message far larger than one read, all arriving intact
- an unknown message type being ignored instead of killing the connection
- killing the server under a live client, asserting the drop is noticed once
  and that the client reconnects by itself
- a command sent to one client not reaching another

They need no framework, plain scripts with asserts and exit codes are enough.

## Notes carried over from v0.9

Things that are true about the code but not obvious from reading it:

- The client's connection state lives in a `Connection` object rather than
  module globals specifically so the socket and the connected flag cannot drift
  apart. A dead connection used to look alive, which is what made the client
  spin and never reconnect. Keep new state on that object.
- `type` belongs to the message envelope. A payload field must never be called
  `type`, which is why the config's `TYPE` travels under another name, `role`
  from v1.0 on. `send_message` refuses a payload that fights over the name.
- Commands are loaded from a list of folders, shared first and then the side's
  own, and a later folder wins. Device loading keeps the same signature so it
  can grow into several folders later, but v1.0 loads from `client/devices/`
  only.
- `print_message` writes to stdout while holding a lock, from inside the event
  loop. On a real console this is fine. If output is ever piped somewhere slow,
  a full pipe buffer will block the whole loop.
