# v1.5 specification

**Theme:** the server in a container.

Today the server runs from a checkout: Python installed by hand, the
dependencies installed by hand, a console window that must stay open. v1.5
packs it into a Docker image that starts with one command, restarts on its
own after a reboot or a crash, keeps everything it knows in one folder, and
stops cleanly when Docker stops it. The same image runs on a Windows PC with
Docker Desktop and on a Raspberry Pi or a NAS with Docker Engine, which is
where a home server belongs.

Written as an implementation brief, the same way as
[v1.4-spec.md](v1.4-spec.md): every decision below is already made, so the work
is to build it, not to redesign it. Where something was deliberately left out,
it says so and why.

## Scope

**In**

1. The server ready for a container: its data folder from an environment
   variable, a clean stop on `SIGTERM`, the address people use printed right
2. The image and the compose file: a small image with the server only,
   `docker compose up -d` to run it, the data folder as one mounted folder,
   a health check, host networking as an option for discovery
3. The guide: installing, running, the console, certificates, backups,
   updating, moving an existing server into the container, and the launcher
   with a server in Docker; a CI job that builds and runs the image

**Out, and why**

| Not doing | Reason |
| --- | --- |
| Clients in containers | A client is a device, later with real hardware (GPIO, USB, Bluetooth) that a container reaches only with extra rights per device. The launcher runs clients. |
| Publishing the image (GitHub Container Registry, Docker Hub) | It needs version tags, images for arm64 and amd64 from one build, and a decision on who may pull. `docker compose up --build` builds locally in about a minute. Later. |
| The launcher starting and stopping the container | The launcher would have to call Docker; two ways to run the server is enough for one version. The launcher finds and uses a server in Docker like any server elsewhere. |
| A reverse proxy, Let's Encrypt | The dashboard is for the house, with the project's own authority since v1.2; a public certificate needs a public name. |
| Kubernetes, Swarm | One server in one house. |
| `uvloop` in the image | The standard loop serves a house many times over; one dependency less to build on arm64. |

## Design

### The data folder

Everything the server writes already lives next to its `config.json`
(v1.3): `pyhome.db` and its WAL files, `certs/`, backups, the imported
`clients.json`. TLS paths are relative to that folder too. So the container
needs exactly one folder from the outside, mounted at `/data`.

**`PYHOME_DATA`** is a new environment variable: the server's data folder.
When it is set and `--config` is not given, the config is
`$PYHOME_DATA/config.json`, and a missing one is made from the example the
image carries (`server/data/config.example.json`, which stays visible since
the mount is at `/data`, not over it). Without the variable nothing changes:
`server/data/config.json` as today.

**A bind mount, not a named volume.** `docker-compose.yml` mounts
`./server-data` from the checkout. The files are where a person can open them:
`config.json` to edit, `ca.crt` to copy, `pyhome.db` for the DB browser,
backups to keep. `server-data/` is ignored by git.

### Stopping

`docker stop` sends `SIGTERM`, waits, then kills. Today `SIGTERM` ends the
server at once: no orderly shutdown, the store not closed. From v1.5 the
server handles `SIGTERM` exactly like the `shutdown` command since v1.4: the
dashboard stops its own way, client connections end while the store can
still record them, the store is closed, exit code 0. The log says
`<name> is shutting down (SIGTERM)`. On Windows, where asyncio has no signal
handlers, nothing changes; a server in a container is always Linux.

`stop_grace_period` is 15 seconds; a clean stop takes about one.

### The address people use

Inside a container the server's own address is the container's (`172.x`),
which nobody outside can reach. **`PYHOME_ADDRESS`** is a new optional
environment variable: the address of the computer the container runs on, as
the house reaches it (`192.168.1.20` or `dom.lan`). When set, the server
prints it in place of its own for the dashboard, and `make_certs.py` adds it
to the certificate's names, so the certificate made inside the container is
valid for the address phones and clients use. Unset, the output is as today.

### The image

- `python:3.13-slim`, one stage. Every dependency has wheels for amd64 and
  arm64, so nothing is compiled.
- `tzdata` installed and `TZ` from the compose file (`Europe/Bratislava`):
  times are stored in UTC and shown in the computer's zone since v1.3, and a
  container's zone is UTC unless told otherwise.
- Only `shared/`, `server/` and `requirements.txt` are copied. A
  `.dockerignore` that starts with `*` and lets in only those keeps
  `config.json`, the database, the certificates and the clients out of the
  build context, so a token can never end up in an image layer.
- A user `pyhome` with uid 1000 runs the server, never root.
- `ENV PYHOME_DATA=/data PYTHONUNBUFFERED=1`, `VOLUME /data`,
  `EXPOSE 50000 50001 50002/udp`.
- **Health check:** `server/healthcheck.py` reads the config and asks the
  dashboard's `/` on `WEB_PORT`, over HTTPS without verifying when TLS is on
  (it asks itself on `127.0.0.1`). Every 30 seconds; `docker ps` shows
  `healthy`.

### The compose file

`docker-compose.yml` at the root of the repository:

```yaml
services:
  server:
    build: .
    container_name: pyhome
    restart: unless-stopped
    ports:
      - "50000:50000"        # clients
      - "50001:50001"        # dashboard
      - "50002:50002/udp"    # Find servers
    volumes:
      - ./server-data:/data
    environment:
      TZ: Europe/Bratislava
      # PYHOME_ADDRESS: 192.168.1.20
    stdin_open: true
    tty: true
    stop_grace_period: 15s
```

`stdin_open` and `tty` give the server a terminal, so `docker attach pyhome`
is its console with the prompt, as in a window (leave with Ctrl+P Ctrl+Q;
Ctrl+C would stop it). `docker compose logs -f` shows the output without the
console.

A port changed in `config.json` must be changed in `ports` too; the guide
says so where it shows the file.

### Discovery from a container

Docker's default network forwards ports, not broadcasts. **Hľadať servery**
on the same computer works (it also asks `127.0.0.1`, and the UDP port is
published); from another computer the broadcast never reaches the container.

`docker-compose.host.yml` is an override for Linux hosts (the Pi, a NAS) that
sets `network_mode: host`: the server is on the house's network directly,
discovery works from every computer, and the printed addresses are right
without `PYHOME_ADDRESS`.

```
docker compose -f docker-compose.yml -f docker-compose.host.yml up -d
```

Docker Desktop on Windows has no usable host networking, so there the
server is typed by address on other computers, or discovery is off.

### The launcher and a server in Docker

Nothing new is needed: with the server in Docker, the launcher's server row
stays unticked, and a client is made with **Hľadať servery**. The container's
server is not "here" (its config is in `server-data/`, not in
`server/data/`), so the form asks for its token and downloads its `ca.crt`,
checked against the fingerprint, exactly as for a server on another computer.

## Part 1: The server ready for a container

- `PYHOME_DATA` in `shared/config.py` and the server's `app.py`; the client
  ignores it
- `SIGTERM` as an orderly shutdown in `server/app.py` (not on Windows)
- `PYHOME_ADDRESS` in the printed dashboard address and in `make_certs.py`
- README: the two variables in the configuration section

### Done when

A server started with `PYHOME_DATA` pointing at an empty folder makes its
config there and keeps its database there; `kill -TERM` ends it with code 0,
`is shutting down (SIGTERM)` in its log and no WAL file left; and with
`PYHOME_ADDRESS` set, the dashboard line and a new certificate name that
address.

## Part 2: The image and the compose file

- `Dockerfile`, `.dockerignore`, `docker-compose.yml`,
  `docker-compose.host.yml`, `server/healthcheck.py`
- `server-data/` in `.gitignore`

### Done when

`docker compose up -d --build` on a fresh checkout builds the image and
starts a server that makes `server-data/config.json`; `docker ps` shows it
`healthy`; a client from the checkout connects to it; `docker attach` gives
the console; `docker compose stop` ends it cleanly; `docker compose up -d`
again starts it with the same clients known; and the image contains no
`config.json`, database or certificate (`docker run --rm pyhome-server ls
/app/server/data` lists only the example).

## Part 3: The guide

`docs/docker.md`, linked from the README:

1. Installing Docker: Docker Desktop on Windows, Docker Engine on the Pi
2. Starting: `docker compose up -d --build`, the first `config.json`, the
   token, `PYHOME_ADDRESS`
3. The console and the logs
4. Certificates inside the container:
   `docker compose exec server python make_certs.py --dir /data/certs --host 192.168.1.20`,
   then `TLS_CERT` and `TLS_KEY` in `server-data/config.json` and a restart
5. Backups: `data backup` in the console writes into `server-data/`;
   copying the folder while the server is stopped is a full backup
6. Updating: `git pull`, `docker compose up -d --build`; the data stays
7. Moving an existing server: stop it, copy `config.json`, `certs/` and
   `pyhome.db` from `server/data/` into `server-data/`, start the container;
   the clients and their history come along
8. Discovery, host networking and the firewall
9. The launcher with a server in Docker

### Done when

Someone who has never used Docker can follow the guide from an empty
Windows PC to a server in Docker with TLS, a client connected from the
launcher, and a backup made.

## Protocol

Nothing changes: the server in a container is the same server.

## Order of work

1. **Part 1** first: the image relies on `PYHOME_DATA` and a clean `SIGTERM`.
2. **Part 2**, built and run in a scratch checkout first, as before.
3. **Part 3** last, written while following it step by step.

Each part gets its own implementation plan in `docs/superpowers/plans/`, is
built and verified in a scratch checkout first, and is finished, tested and
committed before the next one starts.

## Tests

pytest, as in `tests/`, and a new CI job.

- **Part 1:** the config from `PYHOME_DATA`, made from the example when
  missing, `--config` still winning; `SIGTERM` to a real server ends it with
  code 0, the log line and no WAL file (skipped on Windows); `PYHOME_ADDRESS`
  in the printed lines and in the certificate's names
- **Part 2:** `.dockerignore` keeps `server/data/config.json`, `*.db`,
  `certs/`, `client/` and `launcher/` out of the build context (checked by
  building a context listing, without Docker); the health check against a
  real server, with and without TLS
- **CI, a job `docker` on Ubuntu:** build the image, start it with the compose
  file on a temporary data folder, wait for `healthy`, ask `/api/clients`,
  find it with the launcher's discovery on `127.0.0.1`, connect a client from
  the checkout, `docker compose stop`, then check exit code 0, the log line,
  no WAL file, and an image without configs. Windows runners cannot run
  Linux containers, so the job runs on Ubuntu only.

## Honest limits

- **Broadcast discovery from other computers needs host networking**, which
  Docker offers on Linux only. On Windows the server is typed by address.
- **A bind mount on Linux belongs to uid 1000.** The container writes as uid
  1000, the first user on a Pi or most Linux machines. Another owner needs
  `chown 1000 server-data` once; the guide says so.
- **The image is built, not downloaded.** Every computer builds its own,
  about a minute, until publishing comes in a later version.
- **Docker Desktop must be running on Windows** for the server to run; it
  starts with Windows if set to.
- **The container is the server only.** Devices, the launcher and the
  dashboard's phones stay where they are.
