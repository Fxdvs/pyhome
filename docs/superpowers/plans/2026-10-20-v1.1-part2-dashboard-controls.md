# v1.1 Part 2: Device controls on the dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** With a `TOKEN` set, the dashboard turns the light on and off, sets its brightness, switches the thermostat and changes its target; each change shows in the card at once and on the server console; a refused value shows the device's own error; a client that stops answering or disconnects mid request shows that instead of hanging. A server without a `TOKEN` never gets browser controls.

**Architecture:** `send_command` refuses an action the client does not list (plus `get_state`) before anything is sent, so the console's `do` and the browser share one readable refusal. `web_handler.py` gains `POST /api/clients/{client_id}/do` behind `require_token` and a new `require_controls` (403 without a server token). The route is thin: it reads the JSON body and hands it to `dashboard_do(client_id, body, source, timeout)`, which validates the body, prints the console line, awaits `send_command` in the same event loop and maps each outcome to a status and body. `/api/status` gains `controls`. The page draws controls only when `controls` is true, sends actions with the token, and updates the grid card by card so a running request or a dragged slider is never redrawn under the user.

**Tech Stack:** Python 3.10+, FastAPI (`Request`, `Depends`), asyncio, plain JavaScript in `server/web/index.html`. Tests are plain scripts run by `py tests/run_all.py`.

**Spec:** `docs/v1.1-spec.md`, section "Part 2: Device controls on the dashboard".

**Verified:** this plan's code was built and run once in a scratch checkout before it was written down. Every test file passes (`test_launcher.py` needs `tkinter`, which the cloud container lacks). In Chromium, with a real server, a light and a thermostat: the switches, the slider (dragged across a poll, one request on release), **−** / **+**, the device's error above 30 °C disappearing after 4 s, a stopped client giving "no answer within 5 s", a killed client giving "client disconnected", and a phone width viewport with touch.

## Global Constraints

- Controls exist only on a server with a `TOKEN`. Without one, `POST .../do` is 403 and the page draws no controls.
- The route and `dashboard_do` run in the server's one event loop. No threads, no queue: `clients_lock` and the pending request futures belong to that loop.
- `params` values are `bool`, `int`, `float` (finite) or `str`. Nothing nested.
- The unknown action check lives in `send_command`, so `do` on the console gets it too.
- A device refusing a value is `200 {"ok": false, "error": ...}`. Transport problems are status codes: 400, 404, 502, 504.
- Every browser action prints one gray console line. Values from a client or a browser go through `printable()` first.
- The web API takes full ids only.
- The protocol does not change.
- Match the surrounding code: lowercase `#` comments that say why, short docstrings, no type annotations except `request: Request`, which is how FastAPI hands over the raw request. Page comments in Slovak.
- Tests need no framework: plain scripts using `tests/helpers.run_tests(globals())`.
- Work happens on branch `claude/admiring-ptolemy-mfwswb`. `VERSION` stays `1.0` until v1.1 is finished.

**Behaviour:**
- `controls` comes from `/api/status`. A failed read (server down, file opened from disk) means no controls, so demo data is never clickable.
- Light: the switch is a button (`turn_on` / `turn_off`); an invisible range input lies over the brightness track. `input` only moves the fill, `change` (on release) sends `set_brightness` once.
- Thermostat: the header icon becomes an on and off switch; **−** and **+** send `set_target` with the target ±0.5, rounded to halves.
- Anything else: each capability chip becomes a button that sends the action with no params.
- While a request runs, the card shows a spinner and its controls are disabled. The answer's `state` updates the card at once. An error shows as a red line in the card for 4 s.

- A 401 on an action logs out, as a 401 on a poll does.
