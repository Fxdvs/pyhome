# v1.3 specification

**Theme:** the server remembers what it knows.

Today the server forgets almost everything when it stops. `clients.json`
keeps only ids and names, as a list. The last state of every device lives in
memory, so after a restart the dashboard is empty until each client speaks
again, and nothing records what happened in the house. v1.3 moves the
server's memory into one SQLite database: who is in the house, the last state
of every device, and a 90 day history of every change.

Written as an implementation brief, the same way as
[v1.2-spec.md](v1.2-spec.md): every decision below is already made, so the work
is to build it, not to redesign it. Where something was deliberately left out,
it says so and why.

## Scope

**In**

1. A SQLite store for the server, with `clients.json` imported once
2. The last device state survives a restart, and every change goes into a
   history kept for 90 days
3. The dashboard and the console show what the server remembers: offline
   devices, their last state, the history

**Out, and why**

| Not doing | Reason |
| --- | --- |
| A database server (PostgreSQL, MySQL) | One server process writes, on one computer. SQLite is built into Python and needs nothing installed or running. The store is one module, so a different database later touches one file. |
| A cloud database as the store | The house must work without internet. A cloud copy for remote viewing can come later as an add-on, never as the only store. |
| History charts on the dashboard | The history is recorded and readable through the API and the console. Drawing it is its own piece of work. |
| Devices loaded from several folders | Planned for 1.3 earlier, but it has nothing to do with memory and still nothing needs it. Moved to "later". |
| Encrypting the database | Same as the configs: the server computer itself is trusted. |
| Storing the token or keys in the database | They stay in the config and `certs/`, where they already are. |

## Why SQLite

| | JSON files | **SQLite** | Cloud database |
| --- | --- | --- | --- |
| Installed | nothing | **nothing, `import sqlite3`** | account, internet, keys |
| Works without internet | yes | **yes** | no |
| Survives a crash mid write | only if built by hand | **yes, transactions** | yes |
| History and questions about it | hard | **SQL** | SQL |
| In a Docker container | a volume | **a volume, one file** | nothing local |

One server process writing to a file on a local disk is exactly what SQLite is
built for. It stops fitting only with several servers sharing one database, or
a database on a network share (SMB, NFS), neither of which this project does.

## Ready for Docker

The server is meant to run in a container one day (planned as v1.5). That
works with SQLite if the database is on a volume, so v1.3 fixes one rule:

**Everything the server writes lives in its data folder**, the folder of the
config file in use: `config.json`, `certs/` and the new `pyhome.db`. One
volume over that folder keeps everything a container rebuild must not lose.
`server/data/` already is that folder; v1.3 writes nothing anywhere else and
the README says so.

## Part 1: The store

### Design

**One module, `server/handlers/store.py`.** Nothing else in the server imports
`sqlite3`. The rest of the code calls functions such as
`store.upsert_client(...)` and never sees SQL, so a different database later
replaces one file.

**One file, `pyhome.db`, next to the config** (`get_config_path()`'s folder),
like `clients.json` today. A server started with `--config` keeps its own
database.

**One connection, used only from the event loop.** `sqlite3` calls are
synchronous. They are not moved to threads: a write here is a single small
row, well under a millisecond with the settings below, at most a few per
second in a house. Threads would bring locking and the connection's thread
rules for no measurable gain. `check_same_thread` stays on, so a call from
another thread fails loudly instead of corrupting anything.

Opened with:

```python
connection = sqlite3.connect(path, isolation_level=None)  # autocommit, explicit transactions
connection.execute("PRAGMA journal_mode = WAL")    # readers never block the writer
connection.execute("PRAGMA synchronous = NORMAL")  # safe with WAL, much faster
connection.execute("PRAGMA foreign_keys = ON")
```

**Schema version in `PRAGMA user_version`.** `store.open(path)` reads it and
runs every migration above it in order, each in one transaction. Version 1 is
the schema below. A database newer than the code (a downgrade) stops the
server with `pyhome.db is version N, this server knows up to M`, rather than
guessing.

```sql
CREATE TABLE clients (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    device       TEXT,                 -- NULL for a client without a device
    capabilities TEXT NOT NULL,        -- JSON list
    first_seen   TEXT NOT NULL,        -- ISO 8601 UTC
    last_seen    TEXT NOT NULL
);

CREATE TABLE device_state (
    client_id  TEXT PRIMARY KEY REFERENCES clients(id) ON DELETE CASCADE,
    state      TEXT NOT NULL,          -- JSON object
    updated_at TEXT NOT NULL
);

CREATE TABLE state_history (
    id        INTEGER PRIMARY KEY,
    client_id TEXT NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
    at        TEXT NOT NULL,
    state     TEXT NOT NULL,           -- the whole state after the change
    source    TEXT NOT NULL            -- client, console, dashboard 192.168.1.30
);
CREATE INDEX state_history_client_at ON state_history (client_id, at);
CREATE INDEX state_history_at ON state_history (at);
```

Times are ISO 8601 text in UTC (`2026-10-21T18:42:07Z`): readable in any
SQLite browser, and they sort correctly as text.

**Clients.** On every accepted handshake the server upserts the client: name,
device and capabilities are overwritten with what the client says now,
`first_seen` is kept, `last_seen` is set. On disconnect `last_seen` is set
again. This replaces `save_client` and `clients.json`.

**`clients.json` is imported once.** When the `clients` table is empty and a
`clients.json` lies next to the config, its entries are inserted (`ID`,
`NAME`, nothing else is known; `first_seen` and `last_seen` are the import
time), and the file is renamed to `clients.json.imported`. Renamed, not
deleted: it is the backup if anything goes wrong, and the rename is what makes
the import run once. `.gitignore` already covers `server/**/clients.json`; it
gains `server/**/clients.json.imported` and `server/**/pyhome.db*` (the WAL
files are `pyhome.db-wal` and `pyhome.db-shm`).

**Startup.** `app.py` opens the store before the listener starts and prints
one line: `Database server/data/pyhome.db, 4 clients known`. A database that
cannot be opened (no permission, a file that is not SQLite) stops the server
with the reason, the same rule as a broken certificate.

### Done when

A fresh server creates `pyhome.db` at version 1; a server with an old
`clients.json` imports it once and renames it; a client that connects is in
the `clients` table with its device and capabilities; a database from a newer
version stops the server with a clear message.

## Part 2: State and history

### Design

**The last state is stored.** Wherever the server sets `last_state` today (an
unprompted `state` message, a successful `result`), it also writes
`device_state`. When a client connects, `connected_clients[addr]["last_state"]`
starts from the stored state instead of `None`, so the dashboard shows the
light as it was the moment it reconnects; the client's own unprompted state
then replaces it a moment later as before.

**Only changes go into the history.** A state is written to `state_history`
only when it differs from the stored one. `state <id>` asked every minute,
or a client reconnecting in the same state, adds nothing. Comparison is on the
parsed JSON, so key order does not matter.

**Every entry says where it came from.** `source` is:

| Source | When |
| --- | --- |
| `client` | the client sent `state` on its own (connect, or a change made on the device) |
| `console` | the result of `do` or `state` typed on the server |
| `dashboard 192.168.1.30` | the result of a browser action, with its address |

`send_command` gains a `source` parameter, defaulting to `console`;
`dashboard_do` passes `dashboard <address>`. The result handler already knows
which request a result answers, so the source travels with the pending
request.

**90 days.** `HISTORY_DAYS` in the server config, default `90`. Older rows are
deleted at startup and then once a day by a small task in `app.py`'s
`asyncio.gather`. `0` keeps nothing (only the last state), and the README says
that a negative value is treated as `0`.

**Size, to be honest about it.** A light switched 50 times a day stores about
4500 rows in 90 days, roughly half a megabyte. Ten such devices stay under
10 MB. The retention is what keeps it there.

### Done when

After a restart, a light that was on shows as on before its client
reconnects; switching it from the console and from the dashboard adds one
history row each with the right source; asking `state` repeatedly adds
nothing; rows older than `HISTORY_DAYS` are gone after startup.

## Part 3: Showing what the server remembers

### Design

**The API knows offline clients.** `GET /api/clients` returns every known
client, not only connected ones:

```json
{"id": "kuchyna-svetlo", "name": "Kuchyňa svetlo", "online": false,
 "host": null, "port": null, "device": "light", "capabilities": ["turn_on", "..."],
 "last_state": {"on": true, "brightness": 40}, "last_seen": "2026-10-21T18:42:07Z"}
```

`online` is new and `last_seen` is new; `host` and `port` are `null` while
offline. Online clients come first, then offline ones by `last_seen`, newest
first. `POST .../do` to an offline client stays a 404.

**History over the API.** `GET /api/clients/{id}/history?limit=50` (token
required, as for `/api/clients`) returns the newest entries first:
`{"history": [{"at": "...", "state": {...}, "source": "dashboard 192.168.1.30"}]}`.
`limit` is 1 to 500, default 50. An unknown id is 404.

**The dashboard shows offline devices.** An offline card is drawn the same way
but grayed, without controls, with "Offline, naposledy 18:42" instead of the
address. The overview counts online and known clients separately
("2 online z 4"). The page needs no other change: the cards already render
from `last_state`.

**The console.**

- `list` reads from the store: every known client, online ones in green with
  their address, offline ones gray with `last seen 21.10. 18:42`.
- `history <id or start of id> [n]` prints the last `n` changes (default 10)
  with time, source and state. Prefixes work as for `do`, and an offline
  client can be named too, by its full id.
- `data clients clear` clears the `clients` table, which removes their state
  and history with it (`ON DELETE CASCADE`). It asks first, as today, but the
  question no longer blocks the server: today it calls `input()` inside the
  event loop, so the server answers no client and no browser until someone
  types y or n. The answer is read off the loop, the way the prompt itself is.
- `data backup` writes a consistent copy to `pyhome-backup-<date>.db` next to
  the database with SQLite's backup API, safe while the server runs. Copying
  `pyhome.db` by hand is only safe with the server stopped, because of the WAL
  files; the README says so.

### Done when

With one client online and one known but offline, the dashboard shows both,
the offline one grayed with its last state and time, and controls only on the
online one; `list` shows both; `history kuch` prints the light's changes with
sources; `data backup` makes a copy SQLite opens; and `data clients clear`
leaves the server answering clients while it waits for y or n.

## Protocol

**No change.** Everything in v1.3 is on the server. A 1.2 client works with a
1.3 server.

## Order of work

1. **The store** first: the schema, opening, migrations, clients, the import.
2. **State and history** second, on top of the store.
3. **What the dashboard and the console show** last.

Each part gets its own implementation plan in `docs/superpowers/plans/`, is
built and verified in a scratch checkout first, and is finished, tested and
committed before the next one starts.

## Tests

Plain scripts with asserts, as in `tests/`, run by `py tests/run_all.py`.
Every test uses a database in its temp folder, never `server/data/`.

- **Part 1:** a fresh database is version 1 with the three tables; opening it
  again changes nothing; a database marked as a newer version is refused;
  upserting a client keeps `first_seen`; the `clients.json` import runs once,
  renames the file and survives an empty or broken file; WAL mode is on
- **Part 2:** a state that changed adds one history row, the same state adds
  none, key order does not matter; the source is right for client, console and
  dashboard; reconnecting starts from the stored state; retention deletes only
  rows older than `HISTORY_DAYS`, `0` deletes all history
- **Part 3:** the API's online and offline entries and their order; the
  history endpoint's limit, order and 404; `list`, `history` and `data backup`
  output; `data clients clear` leaves the event loop free while it asks
- **End to end:** a real server stopped and started again keeps the light's
  state and history; the dashboard shows the offline client

## Honest limits

- **Copying `pyhome.db` while the server runs can give a broken copy**
  because of the WAL files. Use `data backup`, or copy with the server stopped.
- **The history knows what the server saw.** A change made on a device while
  the server was down is recorded as one jump when the client reconnects.
- **One database per server.** Two servers on one `pyhome.db`, or the file on
  a network share, is not supported.

## Version

`VERSION` in both default configs becomes `1.3`. `docs/versions/v1.3.md` is
written when the version is finished, and its row in the README roadmap is
struck.
