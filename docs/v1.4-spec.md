# v1.4 specification

**Theme:** easy setup, one window for the whole house.

Today `launcher.pyw` is a Tkinter list with checkboxes. It starts every app in
a console window of its own, five apps mean five windows, and a new device
means writing JSON by hand, copying `ca.crt` and pasting the token. v1.4
replaces it with a desktop app: the server and every client in a sidebar, each
app's output and command line inside the window, a form for new clients, and
a button that finds the server on the network.

Written as an implementation brief, the same way as
[v1.3-spec.md](v1.3-spec.md): every decision below is already made, so the work
is to build it, not to redesign it. Where something was deliberately left out,
it says so and why.

## Scope

**In**

1. Configs in the launcher: create and edit client configs and the server
   config in a form, tokens and certificates by button, and real configs kept
   out of git
2. The desktop launcher: an HTML and Tailwind window on pywebview, apps
   running inside it with their output and a command line, the selection
   remembered
3. Finding the server: a button that asks the network which pyhome servers
   are there and fills the client form from the answer

**Out, and why**

| Not doing | Reason |
| --- | --- |
| Tauri or Electron | pywebview uses the same system web view as Tauri (WebView2 on Windows) and keeps the backend in Python, so the launcher's tested logic carries over. The frontend talks to the backend through one small adapter, so a Tauri shell later replaces the shell and keeps every page. |
| An installer or a single `.exe` | Packaging (PyInstaller, signing) is its own piece of work. `launcher.pyw` keeps being started by double click. |
| Pairing with a code | The token already says who may connect. Discovery fills in the address, the token stays something you type or copy. |
| Several servers in one checkout | They would share one `pyhome.db`, which v1.3 rules out. |
| Light theme for the launcher | The launcher is deliberately dark glass, see Design. The web dashboard keeps its own look for now. |
| Keeping the Tkinter launcher | Two launchers to maintain for one job. Its logic moves into the new one with its tests. |

## Design

Dark glass in the style of macOS: a translucent window over a soft, dark,
colored backdrop, a glass sidebar with every app and a status dot (green
running, gray stopped, red exited with an error), the selected app's console
on the right, a glass sheet sliding in for a new or edited client, the system
blue as the only accent. The approved mockup is
[Pyhome Launcher](https://claude.ai/artifact/1KoZ1oBxefuX5JCcJWMuVv); its
layout, colors and wording are the target. Texts are in Slovak, like the
dashboard.

Colors and type are Tailwind theme tokens in one place
(`launcher/web/tailwind.css`), so a light theme or another accent later is a
token change.

## Architecture

```
launcher.pyw                 opens the window, nothing else
launcher/
  core.py                    configs: list, read, validate, write, tokens, certificates
  runner.py                  starts apps with pipes, keeps their output, writes their input
  discovery.py               asks the network for servers
  api.py                     the methods the page calls, built on the three above
  state.json                 what was ticked and selected, not in git
  web/
    index.html, app.js       the page, plain JavaScript, no framework
    tailwind.css             the Tailwind source with the theme tokens
    launcher.css             the built CSS, committed, so running needs no build step
```

**Python owns everything that touches the computer**, the page only draws.
The page calls `window.pywebview.api.<method>()`, which pywebview turns into a
call to a method of `launcher.api.Api` and a JSON answer. Every call goes
through one file, `app.js`'s `backend` object, so a different shell later
changes that file only.

**Output by polling, not pushing.** The page asks
`api.output(app_id, since)` every 250 ms for the lines after the last one it
has. pywebview can push into the page too, but a push arriving while the page
reloads is lost; a poll cannot lose anything, and four calls a second is
nothing for a local window.

**Tailwind without Node.** The CSS is built with Tailwind's standalone CLI, a
single executable. The built `launcher.css` is committed, so starting the
launcher needs Python and `pywebview` only. A test checks that the build is
current: it fails when `tailwind.css` or the pages changed without a rebuild.

## Part 1: Configs in the launcher

### Real configs leave git

`server/data/config.json` and `client/data/config.json` are tracked today, so
a real `TOKEN` put there ends up in `git diff` and, with `git add .`, on
GitHub. From v1.4:

- the tracked files are `server/data/config.example.json` and
  `client/data/config.example.json`, the current defaults with an empty token
- `.gitignore` gains `server/data/config.json` and `client/data/*.json` with
  `!client/data/*.example.json`
- when the default `config.json` is missing, the app copies the example to it
  on start and says so in one line; `--config` with a missing file still stops
  with the error it gives today
- the launcher lists `client/data/*.json` without the examples

**The one step to take when pulling this change.** Git deletes a file from
the working folder when a pulled commit stops tracking it. So before pulling
v1.4 the configs are copied aside and put back after; the README and the
version notes give the three commands:

```
copy server\data\config.json server\data\config.mine.json
copy client\data\config.json client\data\config.mine.json
git pull
```

then rename the `.mine.json` files back. A config that was never committed,
such as `client/data/kuchyna-svetlo.json`, is not touched by the pull.

### The form

**New client** and **Edit** open the sheet from the mockup:

| Field | Rule |
| --- | --- |
| Name | anything, required |
| ID | filled from the name as you type (`Spálňa svetlo` becomes `spalna-svetlo`), editable, must follow the id rule from v1.1, must not be another config's id |
| Device | one of the folders in `client/devices/`, or none |
| Server | an address and a port, typed or picked from Find servers |
| Use the server's token | when the server runs from this checkout, its `TOKEN` is copied in; otherwise a field to paste it |
| Use TLS | copies `server/data/certs/ca.crt` to `client/data/certs/ca.crt` and sets `TLS_CA` |

The file is named after the id (`client/data/spalna-svetlo.json`). Saving
validates everything first and writes once; a wrong field is marked in the
form with the reason, nothing is written. Editing a running client asks to
restart it.

**The server's settings** open the same sheet with: name, ports, token
(**Generate** makes `secrets.token_urlsafe(16)`), history days, and TLS
(**Make certificates** runs `make_certs.py` and shows its output, then sets
`TLS_CERT` and `TLS_KEY`).

All of this lives in `launcher/core.py` as plain functions with tests; the
form is only how they are called.

### Done when

On a fresh checkout the apps start from the copied examples; a client made in
the form connects with TLS and the token without a file being opened by hand;
a duplicate id or a malformed one is refused in the form; and `git status`
shows no config.

## Part 2: The desktop launcher

### Apps inside the window

`launcher/runner.py` starts each app as today
(`python app.py --config <file>`), but with `stdin` and `stdout` as pipes and
`stderr` joined to `stdout`, `PYTHONUNBUFFERED=1` and
`PYTHONIOENCODING=utf-8`, and without a console window. A thread per app reads
lines into a buffer of the last 5000; the page polls it. A line typed in the
console is written to the app's `stdin`, exactly what typing in its own
window does today.

**The apps learn that nobody is at a terminal.** `shared.console` redraws the
`> ` prompt around every message, which is right in a console window and
noise in the launcher. It gains `interactive()`, true when both `stdin` and
`stdout` are a terminal; without one the prompt is not drawn and messages are
plain lines. Started by hand in a console, nothing changes.

**Colors survive.** The apps keep their ANSI colors; the page turns the eight
colors and their bright variants into the theme's green, red, yellow and so
on, and drops any other escape code.

**Stopping.** **Stop** asks the app to end the way a person would: it writes
`shutdown` and `y` to its input and waits 3 seconds, then terminates it, then
kills it after 5 more. `app.py` closes the store on its way out, so a server
stopped this way leaves no WAL file behind, which a terminate today does. Closing the launcher with apps running asks: stop them
all, or cancel.

**Remembered.** Which apps are ticked and which one is selected are saved to
`launcher/state.json` on every change and read on start. It is ignored by git.

### Done when

The server and two clients run inside one window; each one's output appears
live with its colors; `do kuch turn_on` typed into the server's console works;
Stop ends the server cleanly (its log says it is shutting down); a client
that fails shows red with its error; and the ticks and selection come back
after a restart of the launcher.

## Part 3: Finding the server

### Design

**The server answers on UDP.** It listens on `DISCOVERY_PORT` (default
`50002`) for a datagram `{"type": "pyhome-discover", "version": 1}` and
answers the sender with:

```json
{"type": "pyhome-server", "version": 1, "id": "dom", "name": "Dom",
 "port": 50000, "web_port": 50001, "tls": true,
 "fingerprint": "64:B8:03:30:...", "token_required": true}
```

The address is the one the answer came from, so a server never has to know
its own. **Never the token**, and nothing else that is secret: this is what
anyone on the network may ask. `DISCOVERY` set to `false` in the server config
turns it off; it is on by default and the startup lines say on which port.

**The launcher asks.** **Find servers** sends the datagram to the broadcast
address of every network the computer is on, and to `127.0.0.1`, waits one
second and lists every answer. Picking one fills the server fields. With TLS
the list shows the fingerprint, the same one `make_certs.py` and the server
print, so it can be compared before `ca.crt` is trusted.

**Limits.** An answer larger than 2 KB, or one that is not this shape, is
ignored. The server answers at most 20 requests a second, so it cannot be used
to flood the network.

### Done when

With a server running on the same machine and one on another, **Find
servers** lists both with name, address, TLS and fingerprint; picking one
fills the form; a server with `DISCOVERY: false` stays silent; and nothing in
the answer is secret.

## Protocol

The TCP protocol does not change. Discovery is a separate UDP exchange; a
v1.3 server simply does not answer it.

## Order of work

1. **Configs** first, `launcher/core.py`, the examples and `.gitignore`: the
   rest builds on them.
2. **The desktop launcher** second, the largest piece.
3. **Discovery** last; the form works without it.

Each part gets its own implementation plan in `docs/superpowers/plans/`, is
built and verified in a scratch checkout first, and is finished, tested and
committed before the next one starts.

## Tests

pytest, as in `tests/`. pywebview itself is not started in CI: everything it
calls is in `launcher/api.py` and below, which are tested directly.

- **Part 1:** reading, validating and writing configs; the id from a name;
  duplicates; token and certificate steps; copying the example on first start;
  `.gitignore` ignoring real configs and keeping examples
- **Part 2:** the runner with a small Python child: output lines, input,
  colors kept, the buffer limit, a clean stop, a kill after the timeout;
  `interactive()` and plain lines without a terminal; `state.json`; the API's
  answers; the built CSS is current
- **Part 3:** a server answering on loopback, the answer's fields, no token in
  it, `DISCOVERY: false`, malformed and oversized datagrams ignored, the rate
  limit
- **The page:** driven in Chromium with a fake `backend`, as the mockup was:
  sidebar states, console output and colors, the form's validation messages

## Honest limits

- **pywebview needs the system web view.** Windows 10 and 11 have WebView2;
  Linux needs GTK or Qt with WebKit installed. The README says how.
- **Discovery is visible to the whole network.** Anyone on it learns that a
  pyhome server runs at that address and on which ports. That is the point of
  it; `DISCOVERY: false` turns it off.
- **The launcher runs apps as the user who started it**, with the same files
  and rights. It is a convenience, not a sandbox.

## Version

`VERSION` in both example configs becomes `1.4`. `docs/versions/v1.4.md` is
written when the version is finished, and its row in the README roadmap is
