**Date:** 2026-09-22
**Versions:** server and client `1.0`
**Specification:** [docs/v1.0-spec.md](../v1.0-spec.md)
**Implementation plans:** [part 1](../superpowers/plans/2026-09-22-v1.0-part1-per-instance-config.md),
[part 2](../superpowers/plans/2026-09-22-v1.0-part2-device-modules.md),
[part 3](../superpowers/plans/2026-09-22-v1.0-part3-token.md)

## Delivered

### Part 1: per instance configuration

- `--config <file>` on both apps, so one checkout runs several clients
- A missing or empty `ID` is generated on first run and written back
- `launcher.pyw` replaces `start_all.bat`: lists the server and every client
  config, starts and stops them, refuses configs that share an ID
- Apps keep their window open after a fatal error

### Part 2: device modules

- `client/devices/` with a `light` and a `thermostat`, chosen by `DEVICE`
- New message types `cmd`, `result` and `state`; `device_type` renamed to `role`
- Server commands `do <id> <action> [value]` and `state <id>`
- Server keeps the last known state of each device, in memory
- Dashboard redesigned in `server/web/index.html`, the API carries device,
  capabilities and state

### Part 3: token

- Shared `TOKEN` checked in the handshake, a wrong one gets `denied` with a reason
- A refused client stops retrying until its config is fixed and `reconnect` is typed
- A server without a token accepts everyone and warns at startup

### Also

- `tests/` with plain scripts, run with `py tests/run_all.py`: handshake,
  framing, unknown message types, reconnect after a server restart, device
  commands and the token
- Python floor raised to 3.10

## Roadmap items closed

3. Per instance configuration so one checkout can run several clients
4. Device modules, so a client can declare what it is and what it can do
5. Authentication during the handshake
