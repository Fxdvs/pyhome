# v1.1 specification

**Theme:** control from the browser, safely.

v1.0 made devices real: a client declares what it is, the server runs its
actions and keeps its state. But only from the server's console, by an id like
`3f9a12bc`. The dashboard shows everything and can do nothing, and it shows it
to anyone who reaches its port. v1.1 puts the dashboard behind the token, lets
it run device actions, and makes clients easy to type: readable ids and short
prefixes.

Written as an implementation brief, the same way as
[v1.0-spec.md](v1.0-spec.md): every decision below is already made, so the work
is to build it, not to redesign it. Where something was deliberately left out,
it says so and why.

## Scope

**In**

1. The dashboard and its API behind the server's `TOKEN`
2. Device controls on the dashboard
3. Readable ids, and an id prefix is enough in console commands

**Out, and why**

| Not doing | Reason |
| --- | --- |
| TLS / HTTPS | The token still travels in plain text, now also from the browser. Encryption is v1.2, see [Honest limits](#honest-limits). |
| User accounts, roles | One household, one secret. Accounts need storage, passwords and a login flow for no gain yet. |
| A separate dashboard token | One `TOKEN` for clients and the browser. Two secrets to keep in step is more to get wrong. |
| Live updates over WebSocket | Polling every 2 s is fast enough for a light switch and is already there. |
| Sending text messages from the browser | `send` is a console and debugging tool, not something a household uses. |
| Addressing by `NAME` | A name is for display: it has spaces and diacritics and two clients may share one. A readable `ID` does the job without turning one into the other. |
| Prefixes in the web API | The API takes the full id. Prefixes are for people typing, the page already knows every id. |
| Login rate limiting | A token from `secrets.token_urlsafe(16)` is 128 bits, guessing it over HTTP is not practical. |

## Part 1: Dashboard behind the token

### Problem

`/api/clients` answers anyone. Once Part 2 adds controls, an open dashboard
would let anyone on the network switch devices, which is worse than seeing them.

### Design

The page itself stays public. `GET /` serves `index.html`, which holds no data,
so there is nothing to protect there, and serving it without a check is what
lets it show the token prompt. Everything under `/api/` is checked.

**How the browser sends the token.** In a header, on every API request:

```
Authorization: Bearer <token>
```

Never in the URL. A token in a query string ends up in browser history,
bookmarks and anything that logs URLs.

**One check, shared with the handshake.** The comparison in
`client_handler.check_token` moves into a function both sides use:

```python
def token_matches(given):
    """True when given is the server's TOKEN. compare_digest, as in the handshake."""
```

`check_token(hello)` keeps its readable reasons and calls `token_matches`.
The web handler uses it through a FastAPI dependency:

```python
async def require_token(authorization: str | None = Header(default=None)):
    """401 unless the Bearer token matches. Does nothing when the server has no TOKEN."""
```

**Answers.**

| Situation | `/api/clients` | `POST` from Part 2 |
| --- | --- | --- |
| Server has a `TOKEN`, request carries it | 200 | runs |
| Server has a `TOKEN`, missing or wrong | 401 `{"error": "token required"}` | 401 |
| Server has no `TOKEN` | 200, as today | 403 `{"error": "set TOKEN on the server to control devices from the browser"}` |

The last row is the important one. **A server without a token keeps its read
only dashboard but never gets browser controls.** Upgrading does not lock
anyone out of looking, and nobody gets an open remote control by forgetting a
setting. The startup warning that already exists for clients gains a second
line for the dashboard.

`/api/status` is new and needs no token:

```json
{"token_required": true, "controls": true}
```

The page reads it first, so it knows whether to ask for a token and whether to
draw controls, without guessing from a failed request.

### The page

- **No token stored and one is required:** the client grid is replaced by one
  card with a password field and a **Prihlásiť** button. Nothing is polled.
- **Token entered:** stored in `localStorage` under `pyhome.token`, then
  polling starts. Stored so a phone does not ask on every visit.
- **A 401 while polling:** the stored token is dropped and the prompt comes
  back with "Nesprávny alebo zmenený token". This is also what happens after
  the token is changed on the server.
- **Odhlásiť** in the header clears the stored token and shows the prompt.
- **Server without a token:** no prompt, the dashboard looks as it does now,
  plus a gray line "Ovládanie je vypnuté, server nemá nastavený TOKEN".

### Done when

With a `TOKEN` set, opening the dashboard asks for it, a wrong one is refused,
the right one shows the devices and survives a page reload, and `curl` without
the header gets 401. Without a `TOKEN`, the dashboard works exactly as in 1.0.

## Part 2: Device controls on the dashboard

### Problem

Everything needed already exists. `send_command(client_id, action, params)` in
`client_handler.py` sends `cmd` and waits for `result`; the console's `do`
command is a thin wrapper around it. The web handler simply has no route to it.

### Design

**It runs in the same event loop.** `server/app.py` runs uvicorn with
`asyncio.gather` next to the TCP listener, so a FastAPI route can `await
send_command(...)` directly. No threads, no queue. Keep it that way: running
uvicorn in a thread would break `clients_lock` and the pending request futures,
which belong to one loop.

**The route.**

```
POST /api/clients/{client_id}/do
{"action": "set_brightness", "params": {"level": 40}}
```

`params` is optional and defaults to `{}`.

**Validation before anything is sent.**

- `action` is a non-empty string
- `params` is an object whose values are `bool`, `int`, `float` or `str`.
  Nothing nested: the console's `key=value` cannot produce more, and the device
  contract was written for flat values.
- `action` is one of the client's `capabilities` or `get_state`.

The last check belongs in `send_command` itself, not in the web route, so the
console's `do` gets the same early, readable refusal instead of a round trip to
the client. `send_command` raises `ValueError("unknown action 'x', this device
has: turn_on, turn_off, set_brightness")`.

**Answers.** The body always says what happened. The status code says whether
the request reached the device.

| Situation | Status | Body |
| --- | --- | --- |
| Device ran it | 200 | `{"ok": true, "state": {...}}` |
| Device refused it (bad value) | 200 | `{"ok": false, "error": "level must be ..."}` |
| Bad body or unknown action | 400 | `{"error": "..."}` |
| No online client with that id | 404 | `{"error": "..."}` |
| Client disconnected while waiting | 502 | `{"error": "client disconnected"}` |
| No answer in `COMMAND_TIMEOUT` (5 s) | 504 | `{"error": "no answer within 5 s"}` |

A refused value is a 200 because the request worked and the device answered,
which is the same split the protocol already makes with `result.ok`.

**The console sees it.** Every action from the browser prints one gray line on
the server console:

```
Dashboard 192.168.1.30 → Kuchyňa#3f9a12bc set_brightness {"level": 40}
```

Whoever runs the server can see what the house is doing, and from where.

### Controls on the page

Built into the cards that exist, not a separate screen.

| Device | Control | Action sent |
| --- | --- | --- |
| `light` | the switch becomes clickable | `turn_on` / `turn_off` |
| `light` | the brightness track becomes a slider | `set_brightness` with `level`, sent on release (`change`, not `input`) so dragging sends one request, not fifty |
| `thermostat` | **−** and **+** around the target | `set_target` with `temperature`, current target ±0.5 |
| `thermostat` | an on and off switch in the header | `turn_on` / `turn_off` |
| anything else | each capability chip becomes a button | that action with no params, the device's defaults apply |

While a request runs, that card's controls are disabled and show a small
spinner. The answer's `state` updates the card at once, without waiting for
the next poll. An error shows as one red line inside the card for 4 seconds.

**Polling must not fight the user.** `render()` replaces the whole grid with
`innerHTML` every 2 s, which would drop a slider mid drag and swallow a click.
Cards get a stable key (`data-id`) and the grid is updated card by card. A card
whose request is still running, or that holds focus, is skipped until it is
done.

### Done when

With two clients running, a light and a thermostat, the dashboard turns the
light on and off, sets its brightness and changes the thermostat's target; each
change shows in the card at once and on the server console; an out of range
value shows the device's own error; and stopping a client mid request shows
"client disconnected" instead of hanging.

## Part 3: Readable ids and id prefixes

### Problem

`send`, `do` and `state` take an id, and since v1.0 a new config gets a
generated one like `3f9a12bc`. Typing it means running `list` first and
copying it.

### Design

Two small pieces. Neither adds a new kind of name: the id stays the one thing
that addresses a client, it just becomes something a person would choose and
can shorten.

**1. A naming convention for ids.** `ID` was never required to be hex, it is
only generated when empty, and the launcher already refuses two configs with
the same one. v1.1 writes the convention down and makes it the default:

| Field | Used for | Rule | Example |
| --- | --- | --- | --- |
| `ID` | typing in commands | `room-device`, lowercase `a-z`, `0-9` and `-`, no spaces or diacritics | `kuchyna-svetlo`, `obyvacka-termostat` |
| `NAME` | display, dashboard and console | anything, diacritics welcome | `Kuchyňa svetlo` |
| server `ID` | the window title and `about` | one word | `dom` |
| config file | the launcher list | same as the id | `client/data/kuchyna-svetlo.json` |

The rule as a regular expression, kept in `shared/config.py`:

```python
ID_PATTERN = re.compile(r"[a-z0-9]+(-[a-z0-9]+)*")
```

**The generated id follows the file name.** When `ID` is empty, `load_config`
takes the config file's name without `.json`, lowercased, if it matches
`ID_PATTERN` and is not `config`. Otherwise it falls back to `uuid4().hex[:8]`
as today. So copying a config to `kuchyna-svetlo.json` and emptying its `ID`
gives it the id `kuchyna-svetlo` on first run. `config.json` keeps getting a
random one, `config` says nothing about the device.

**An id that breaks the rule is a warning, never a refusal.** Existing ids
like `1` or `3f9a12bc` already match. One with a space could never be typed as
a console argument, so:

- the client prints a yellow warning at startup: `ID 'Kuchyňa 1' does not
  follow the id rule (a-z, 0-9 and -), it cannot be typed in commands`
- the launcher shows the same as a note on that row, but still runs it

Nothing is renamed automatically. An id is also the key in `clients.json`,
changing it silently would leave the old entry behind.

**2. A prefix is enough.** A new function in `client_handler.py` that
`send_command` and `send_to_clients` both use:

```python
def find_online_client(target):
    """(addr, info) of the online client target names.

    An exact id wins. Otherwise target is a prefix, compared case
    insensitively, that must match exactly one online client. Raises
    LookupError with a readable message when nothing or more than one matches.
    """
```

- **Exact first.** With `kuchyna` and `kuchyna-svetlo` both online, `kuchyna`
  means the first one, never "ambiguous".
- **Ambiguous is an error, never a guess.** `do kuch turn_on` with
  `kuchyna-svetlo` and `kuchyna-termostat` online answers `'kuch' matches 2
  online clients: kuchyna-svetlo, kuchyna-termostat`. Switching the wrong
  device is worse than asking.
- **Only online clients.** Commands only reach online clients, so an offline
  one never makes a prefix ambiguous.
- **No minimum length.** Uniqueness is the only check. `do k turn_on` works
  while only one online id starts with `k`.
- `all` stays reserved for `send`. A client whose id is `all` is not reachable
  by `send` until renamed, so the client warns about it at startup too:
  `ID 'all' is reserved for send all, choose another`.

**Where it shows.**

- `send`, `do` and `state` say `<id or start of id>` in their usage lines.
- When a command was given a prefix, the success line prints the full id, so
  it is clear which device answered: `✔ kuchyna-svetlo turn_on: {"on": true}`.
- README gets the convention table under Configuration, and its config example
  uses a readable id.
- The default `client/data/config.json` keeps `"ID": "1"`, it is the example
  people copy and changing it would rename an existing client.

The web API keeps full ids only, see Scope.

### Done when

A config copied to `kuchyna-svetlo.json` with an empty `ID` connects as
`kuchyna-svetlo`. With `kuchyna-svetlo` and `obyvacka-termostat` online,
`do kuchyna-svetlo turn_on`, `do kuch turn_on` and `do KUCH turn_on` all reach
the light; with a second `kuchyna-termostat` online, `do kuch turn_on` is
refused and lists both ids; `send all` still reaches everyone; and a config
with `"ID": "Kuchyňa 1"` still connects, with a warning.

## Protocol

**No change.** `hello`, `welcome`, `cmd`, `result` and `state` stay as they are,
which means a 1.0 client works with a 1.1 server and the other way round. All
of v1.1 lives on the server side and in the page.

## Order of work

1. **Token on the dashboard** first. It is small, and controls must never exist
   without it, even for one commit.
2. **Controls** second, the largest piece: route, validation in
   `send_command`, then the page.
3. **Readable ids and prefixes** last. Independent of the other two, and it
   touches the config and the console commands that Part 2 does not.

Each part gets its own implementation plan in `docs/superpowers/plans/`, and is
finished, tested and committed before the next one starts.

## Tests

Plain scripts with asserts, as in `tests/`, run by `py tests/run_all.py`.

- **Part 1:** `require_token` with no server token, right token, wrong token,
  missing header, a header without `Bearer`; `/api/status` in both modes;
  the 403 on `POST` without a server token; `token_matches` shared with the
  handshake still refuses what `test_token.py` refuses
- **Part 2:** the route's answer for each row of the answers table, using a
  fake client as `test_server_devices.py` does; params validation (nested
  value, list, missing action); `send_command` refusing an unknown action
  before anything is written; an end to end test in `test_devices_e2e.py`
  style that starts the real server and a light client and drives it over HTTP
- **Part 3:** the generated id from the file name (`kuchyna-svetlo.json`,
  `config.json`, `Kuchyňa 1.json`), the startup warning, `find_online_client`
  for an exact id, a unique prefix, case, an ambiguous prefix, an exact id
  winning over a longer one it prefixes, offline clients ignored; `send all`
  unchanged

The page's JavaScript is not unit tested. Part 2's done when is checked by hand
in a browser and written down in the implementation plan's last task.

## Honest limits

- **The token crosses the network in plain text, now from the browser too.**
  Anyone who can watch the Wi-Fi traffic can read it and then control devices.
  On a home network behind a WPA2/WPA3 router this is the same risk as in 1.0;
  on a shared or open network it is not acceptable. This is what v1.2 fixes.
- **`localStorage` keeps the token on the device.** Anyone with the unlocked
  phone has the dashboard. **Odhlásiť** clears it.
- **Anyone with a client config can control everything.** The browser and the
  clients share one secret. Fine for one household, not for guests.
